# ecr-repository

One ECR repository with immutable tags, scan on push, and a lifecycle policy that keeps storage bounded. Project 8.

```hcl
module "repository" {
  source   = "../modules/ecr-repository"
  for_each = var.services

  name            = "ci-cd-lab/${each.key}"
  retained_images = 10
}
```

Only `name` is required. Everything else has a default that is safe to ship.

---

## The interface is the contract

**A consumer should be able to use this module from the table at the bottom of this page, without opening `main.tf`.** Variables in, outputs out, and everything between them is private. If a consumer has to read the source to know what a variable does, the interface is broken, even when the code is correct.

What that meant here:

| Decision | Why |
|---|---|
| One required input | Every other input has a default someone can ship without thinking about it |
| `immutable_tags = true`, a bool | The provider wants `"IMMUTABLE"` or `"MUTABLE"`. A bool cannot be misspelled |
| `arn` is an output | `infra/ecr` scopes CI push access to these ARNs. Without the output, the consumer would rebuild the ARN from strings |
| No `force_delete` input | Deleting a repository that holds images should take a deliberate change to this module |
| Provider constraint `>= 5.60, < 7.0` | A module sets the widest range it works with. The root module picks the version (`~> 5.60` in `infra/ecr`). A module that pins tightly conflicts with every root that pinned differently |

The reference below is generated by `terraform-docs`, so it cannot fall out of date with the code without someone noticing:


## `for_each`, not `count`

**Instantiate repeated things with `for_each` over a map. `count` ties each instance to its position in a list.**

Measured with three `terraform_data` stand-ins, where `triggers_replace` does what a name change does to an ECR repository. Starting from `["api", "worker"]`, then inserting `auth` at the front:

| | Plan | What happened |
|---|---|---|
| `count` | `3 to add, 0 to change, 2 to destroy` | `repo[0]` was `api` and is now `auth`; `repo[1]` was `worker` and is now `api`. Both replaced |
| `for_each` | `1 to add, 0 to change, 0 to destroy` | `repo["auth"]` created. Nothing else touched |

With real repositories, that `count` plan replaces two repositories that hold images. Without `force_delete`, ECR refuses to delete a repository that is not empty (`RepositoryNotEmptyException`), so the apply would stop partway instead of deleting images. That was not run here, and it is not a safety net to rely on.

| | How it happens | What goes wrong | What you see |
|---|---|---|---|
| **Insert into a `count` list** | a new service added anywhere but the end | every later index now points at a different item | `must be replaced` on resources nobody edited |
| **Remove from a `count` list** | a service deleted from the middle | the same shift, in the other direction | the last instance destroyed, the rest replaced |
| **`for_each` over a list** | `for_each = var.services` where the variable is a list | Terraform refuses: `for_each` needs a map or a set of strings | `Invalid for_each argument` at plan; wrap it in `toset()` or make it a map |

`count` is still right for one thing: switching a single resource on and off (`count = var.enabled ? 1 : 0`).

> Further reading: [`for_each`](https://developer.hashicorp.com/terraform/language/meta-arguments/for_each)

## Four ways to validate, and where each one is used

**Check an input in `validation`, an assumption in `precondition`, a result in `postcondition`, and ongoing health in `check`.** They run at different times and fail differently, so the choice changes what a failure looks like.

| | Runs | On failure | Used in this repository |
|---|---|---|---|
| `variable` `validation` | at plan, before any resource | plan stops, the error names the variable | `name`, `retained_images`, `untagged_expiry_days` here |
| `precondition` | before one resource is planned | that resource and everything after it stop | `infra/ecr/ci.tf`: no push access for a CI role that any branch can assume |
| `postcondition` | after one resource is read or applied | stops anything that depends on it | not used. It suits a data source whose result you rely on, such as "this AMI is from our account" |
| `check` | at the end of every plan and apply | a warning; nothing stops | not used. It suits health that should be reported, not enforced |

The precondition in `infra/ecr` is the useful one. `infra/ci-oidc` owns the CI role's trust policy and this stack cannot change it. Before Project 8, the rule "a role that can push is pinned to `main` or a tag" existed only as a comment. Now `infra/ecr` reads the trust policy and refuses to grant push access if any subject is open:

```
Refusing to grant ECR push: ci-cd-lab-ci trusts repo:example/ci-cd-lab:*.
Pin its trust policy to a branch or environment in infra/ci-oidc first.
```

> Further reading: [Custom conditions](https://developer.hashicorp.com/terraform/language/expressions/custom-conditions)

## Tests

**`terraform test` with `mock_provider` plans the module without AWS credentials or API calls.** The three files in `tests/`:

| File | Covers |
|---|---|
| `defaults.tftest.hcl` | only `name` given: immutable tags, scan on push, two lifecycle rules in the right order, 10 retained |
| `overrides.tftest.hcl` | every input changed, and each one reaches the resource it controls |
| `validation.tftest.hcl` | four bad inputs, each expected to fail its own validation |

```bash
cd infra/modules/ecr-repository
terraform init && terraform test        # 7 passed, 0 failed
```

A passing test only means something if a broken module would fail it. Each of these was broken on purpose and run again:

| Broken how | Caught by |
|---|---|
| `name` validation deleted | `uppercase_name_is_rejected`: `Missing expected failure` |
| lifecycle rules swapped | `lifecycle_expires_untagged_first_then_keeps_ten` |
| `immutable_tags` ignored | `every_input_reaches_its_resource` |

`expect_failures` is how a negative test is written. The run passes only if that validation fails. Delete the validation and the run fails with `Missing expected failure`.

`infra/ecr/tests/` tests the consumer the same way, including the precondition above, by overriding the CI role's trust policy with an open one.

> Further reading: [Tests](https://developer.hashicorp.com/terraform/language/tests), [Mocks](https://developer.hashicorp.com/terraform/language/tests/mocking)

## Versioning

Every consumer is in this repository, so `source` is a local path and every change reaches every consumer in the same commit. A consumer in another repository would pin a Git ref:

```hcl
source = "git::https://github.com/slavkurochkin/ci-cd-lab.git//infra/modules/ecr-repository?ref=ecr-repository/v1.0.0"
```

A local path has no version. A breaking change here, such as renaming an input, breaks `infra/ecr` in the same pull request, where `terraform test` and `plan` show it. With a Git ref, the same change reaches consumers when they next bump the ref, which may be months later, during something unrelated.

What counts as breaking: removing or renaming a variable or output, adding a required variable, changing a default in a way that changes the plan. That last one is easy to miss. Changing a lifecycle rule's description from "after a day" to "after 1 day(s)" during this project made `infra/ecr` plan to **replace** both lifecycle policies, because any change to the policy JSON forces replacement.
